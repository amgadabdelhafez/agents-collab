## Defaults on (fix8, 2026-10-11)

Owner directive 2026-10-11: the governess Temporal journal and the A2A V2
plane are on by default. Both degrade instead of failing: neither ever blocks a
loop launch or stops the V1 orchestration plane. Branch
`claude/fix8-defaults-on` (from `claude/fix-integration-r7-2026-10-11`).

### Governess Temporal journal: default on for paired tmux runs

Resolution, per governess start and per close (`resolveGovernessTemporalConfig`
in `src/loop/governess-temporal-journal.ts`):

1. `LOOP_GOVERNESS_TEMPORAL=off` (also `0`, `false`, `no`, `disabled`, any
   case): file journal only. Wins over everything below.
2. `LOOP_GOVERNESS_TEMPORAL_ADDRESS` and `_NAMESPACE` set: exactly as fix7
   (both or neither; one alone is still an error).
3. Otherwise the default: address and namespace are read from the
   orchestration config, `LOOP_ORCHESTRATION_CONFIG` or
   `~/.loop/orchestration/config.json` (its `address` and `namespace`; the
   rest of the config is not validated here). Task queue:
   `LOOP_GOVERNESS_TEMPORAL_TASK_QUEUE`, or `loop-governess-<host>` where
   `<host>` is the first label of the host name, lower-cased (on sweetmac14:
   `loop-governess-sweetmac14`). One queue per host satisfies fix7
   precondition 3 without configuration.
4. No config, unreadable, not JSON, or no usable address/namespace: file
   journal only.

The governess logs exactly one line about it in the run's `governess.jsonl`:

- `journal-temporal-recovered` (as in fix7): armed, with the `workflowId`
  `governess-beat:v2:<repoId>:<runId>:loop-governess-<host>`.
- `journal-temporal-off` with `reason`: resolved off (opt-out or absent
  config).
- `journal-temporal-fallback` with `address`, `namespace`, `taskQueue`,
  `source` and `error`: it tried and fell back to the file journal.

Preflight: the connection is dialled with a 3 s connect timeout, then the
namespace is described within 3 s. Failure raises
`GovernessTemporalUnreachableError`. Fallback rules:

- Default source (`orchestration-config`): any failure to arm the journal
  (unreachable, unknown namespace, a foreign execution under the run's id, a
  manifest without a repo id) falls back to the file journal.
- Explicit source (`env`): only an unreachable server falls back; a foreign
  execution or missing repo id still stops the governess, as in fix7, because
  the operator asked for that server.

After a fallback the run never journals to Temporal and its teardown closes
nothing. The launch itself never waits on Temporal: the preflight runs in the
governess pane after the session exists.

The pane receives `LOOP_GOVERNESS_TEMPORAL` and `LOOP_ORCHESTRATION_CONFIG`
through the `governessEnv` allowlist in `src/loop/tmux.ts`, so the pane and
the launcher-side close resolve the same server and queue. The launcher-side
close, `loop reconcile stopped-run|failed-start`, startup reconcile and
`loop governess history` all use the same resolution.

Legacy executions: none are touched. A legacy `governess-beat:<runId>`
execution lives on the old queue `loop-governess`; the default queue is
`loop-governess-<host>`, so the close describes it, reports
`refused-foreign` and leaves it RUNNING (owner, 2026-10-11: no termination
needed). Do not set `LOOP_GOVERNESS_TEMPORAL_TASK_QUEUE=loop-governess` on a
host unless you mean to have that host close its own owned legacy executions.

What it does against the live server once a fix8 binary is installed: every
paired tmux run launched on sweetmac14 journals to `192.168.1.18:7233`,
namespace `harness`, queue `loop-governess-sweetmac14`, one RUNNING
`governess-beat.v1` execution per live run, terminated at teardown (history
kept). No worker polls that queue; the journal writes through
`signalWithStart`, as in gov-6.

Opt out per launch: `LOOP_GOVERNESS_TEMPORAL=off loop ...`. Opt out for a
shell: `export LOOP_GOVERNESS_TEMPORAL=off`.

### A2A V2: `loop orchestration a2a-v2 init <config>`

```
loop orchestration a2a-v2 init <config-path> [--recipient <supervisor-id>]
  [--manifest <supervisor-id>=<absolute run manifest.json>]...
  [--ledger-name <name>] [--ledger-port <port>] [--database-url-env <NAME>]
```

1. Ledger. Unless the config already has `a2aV2`, or `--database-url-env`
   names an already-set variable, init provisions a local PostgreSQL:
   container `loop-a2a-ledger` (`--ledger-name`), volume
   `loop-a2a-ledger-data`, image `postgres:17-alpine@sha256:18cfe3ef...`,
   label `dev.loop.a2a-ledger=1`, `--restart unless-stopped`, published on
   `127.0.0.1:55432` only (`--ledger-port`). The password is generated by
   init and written to two 0600 files next to the config: the env file (in
   the ledger URL) and the secret file `<config-dir>/<container>.password`
   (live: `~/.loop/orchestration/loop-a2a-ledger.password`, the password
   alone). The container mounts the secret file read-only at
   `/run/secrets/loop-a2a-ledger-password` and reads it through
   `POSTGRES_PASSWORD_FILE` (fix8 critic fix 2). The password is never in
   argv, never in any docker call's environment and never in the
   container's environment, so `docker inspect` does not show it. A config
   directory whose path has a comma, a quote or a newline is refused (docker
   `--mount` cannot carry it). The secret file must be visible to the Docker
   daemon: with colima or Docker Desktop that means under the home
   directory, which `~/.loop` is. A container with that name but without the
   label, or a volume whose password is not in the env file, is refused, not
   adopted.
2. Env file `<config-dir>/a2a-v2.env`, mode 0600, created with `O_EXCL` or
   replaced through a 0600 temporary and a rename:
   `LOOP_A2A_V2_DATABASE_URL` and `LOOP_A2A_V2_RESULT_GRAPH_KEY` (32 random
   bytes, base64url). Init never prints either value; it prints the variable
   names. A group- or world-readable env file is refused by init and not read
   by serve (which disables V2 with reason `env-file-mode`, see Serve): chmod
   600 it and rotate what it holds.
3. Config. The `a2aV2` section is built in memory, validated with the
   server's own parser, written to a 0600 temporary next to the config, the
   original is backed up as `<config>.bak-<YYYYMMDDTHHMMSSZ>` (0600, refused
   if that name exists), the original is re-read and compared by SHA-256, and
   the temporary is renamed over it. Section values: `workflowIdFormat`
   `legacy` (owner decision; deployment ids stay off), `databaseUrlEnv`
   `LOOP_A2A_V2_DATABASE_URL`, `resultGraphKeyEnv`
   `LOOP_A2A_V2_RESULT_GRAPH_KEY`, `routePath` `/a2a/v2`, `tenant`
   `tenant:<identity, sanitised>`, `principal` the recipient's principal,
   `endpointRef` from the recipient seat, `sessionTtlMs` 3600000, policy
   claim 300 s, escalation 900 s, 5 attempts, retry 30 s.
4. Idempotent: with `a2aV2` present init changes no config and makes no
   backup; it only keeps its own ledger running (starts a stopped one, and
   recreates a removed container from its kept volume, on the port the env
   file's URL names). A rerun after an incomplete init reuses the container,
   the volume and the password in the env file, and restores the secret file
   if it was deleted (the bind mount needs it to start).
5. Ledgers created by f9a38faa (the first fix8 build) carry
   `POSTGRES_PASSWORD` in the container's environment: `docker inspect
   loop-a2a-ledger` shows the password to anyone who can reach the Docker
   daemon, until the container is recreated. Init accepts such a ledger and
   reuses it as it is (no data or password change), logging one line that
   says so and names the recreate command. To recreate it with the secret
   file (owner; the volume `loop-a2a-ledger-data`, its rows and the password
   are kept; V2 is down from the `rm` until the service restarts):

   ```
   docker rm -f loop-a2a-ledger && loop orchestration a2a-v2 init ~/.loop/orchestration/config.json
   ```

   then restart the service and check `/healthz` shows `"a2aV2":"ready"` and
   `docker inspect --format '{{json .Config.Env}}' loop-a2a-ledger` lists
   `POSTGRES_PASSWORD_FILE=...` and no `POSTGRES_PASSWORD=`. The password
   itself is unchanged by the recreate; rotating it is a separate step
   (`ALTER ROLE loop PASSWORD ...` inside the ledger, then the same value in
   the env file and the secret file) for when it may have been read.

Recipient: the V2 recipient must be a Loop binding, a supervisor with a
`manifestPath` (the run manifest of a live Loop pane whose Codex thread or
Claude session the server enrols). Mailbox-only supervisors cannot be V2
recipients. Init uses `--recipient`, else the first supervisor with a
`manifestPath`; `--manifest <id>=<path>` adds one (absolute, canonical,
regular, a valid run manifest). With none it provisions the ledger and the
env file, writes no section, exits non-zero and names the mailbox-only
supervisors. The live config (2026-10-11) has five mailbox-only supervisors,
so on the live host init stops there until an owner names a Loop run to bind.

Serve (`loop orchestration serve <config>`):

- Reads `<config-dir>/a2a-v2.env` under the process environment (a variable
  already set wins). The other config commands (`result-graph-id`,
  `result-graph-key-fingerprints`, `v2-quarantine*`) read it too.
- No `a2aV2` section: logs `A2A V2 off: run loop orchestration a2a-v2 init
  <config>` and serves V1. `/healthz` has `"a2aV2": "off"`.
- Section present and every check passes: V2 starts as before. `/healthz`
  has `"a2aV2": "ready"`.
- Any A2A V2 start problem disables V2 and never V1 (fix8 critic fix 1):
  exactly one line `A2A V2 disabled (<reason>): <detail>; V1 continues`
  (variable names, paths and fixes only, never a URL or a secret), V1
  serves normally, and `/healthz` has `"a2aV2": "disabled"` and
  `"a2aV2Reason": "<reason>"`. Fix the cause, then restart the service.
  Reasons, in the order they are checked:
  - `config-invalid`: the `a2aV2` section fails validation (its message is
    in the line). V1's part of the config is parsed on its own.
  - `env-file-mode`: `a2a-v2.env` is group- or world-readable. It is not
    read at all (its mode is checked on the open file before any byte is
    read), even when the process environment would satisfy V2. The line
    gives the fix: `chmod 600 <path>`, rotate the secrets it holds, restart.
  - `env-file-unreadable`: `a2a-v2.env` is a symlink, not a regular file,
    cannot be opened, or is malformed.
  - `result-graph-key`: a configured result graph key variable (primary or
    previous) is unset, shorter than 32 bytes, or holds the same key as
    another (named by variable and fingerprint).
  - `database-unset`: the ledger database variable is unset.
  - `database-unreachable`: the ledger does not answer `SELECT 1` within
    5 s.
  - `start-failed`: the V2 service itself did not start (a store or
    migration failure, a recovery refusal naming its quarantine command, a
    workflow id format refusal); the factory's message is in the line, and
    V1 starts on a Temporal host of its own.
- Only V1's configuration refuses start: an invalid V1 part of the config, a
  missing `LOOP_ORCH_TOKEN_*`-style token variable, an unreachable Temporal.
- Recipient enrollment never refuses start (fix8 critic fix 1). The
  configured recipient and its peer seats are enrolled per recipient: one
  whose run is stopped, whose run manifest is missing, whose session is
  absent, or whose rebind is denied is logged once as `orchestration A2A V2
  session enrollment failed for <seat>: <cause>`, counted in `/healthz`
  `notEnrolledCount`, listed on the authenticated assignment status, and
  retried by the existing reconciliation sweep (every 5 s at most) until it
  enrols (`... recovered for <seat>`). Its deliveries wait meanwhile without
  spending attempts, up to the not-enrolled bound. A supervisor binding
  whose manifest does not exist at start routes nowhere until it does (it is
  then checked as before: regular, non-symlink, canonical).

Rollback:

- Config: `cp -p <config>.bak-<stamp> <config>` (the backup is the exact
  original bytes), then restart the service. Or delete the `a2aV2` key: serve
  then logs `A2A V2 off` and runs V1 only.
- Binary: restart the service with the previous binary. A pre-fix8 build
  does not read the env file: export the two variables in the service
  environment, or remove the section first.
- Ledger: `docker stop loop-a2a-ledger` disables V2 at the next restart (V1
  continues). Removal (`docker rm -f loop-a2a-ledger`, `docker volume rm
  loop-a2a-ledger-data`) deletes the ledger's rows and needs explicit owner
  authority.

Limits:

- Ledger password: a ledger created by init since the critic fix holds no
  password in its Docker record. One created by f9a38faa does until it is
  recreated (step 5 above). Anyone who can read the 0600 secret file or the
  env file (the owner, root) can read the password; anyone who can exec into
  the container can read the mounted file.
- The V2 dispatch owner and recipient authority reference carry the config
  identity through `a2aV2IdentityToken` (fix8): characters outside
  `[A-Za-z0-9._:-]` become `-`, so the live `loop-orchestration@sweetmac14`
  enters them as `loop-orchestration-sweetmac14`. Before fix8 an identity
  with `@` failed every V2 start at `governance-store` ("dispatch owner is
  invalid"); found by the fix8 e2e.

### A2A V2 clients: one identity, one token (fix9 client identity, 2026-10-11)

The clients are `loop a2a <enroll|release|send|status|ack> --as
<supervisor-id>`, the `--a2a-as` launch flag, the teardown release hooks,
`loop mailbox ack` (V2 envelopes), and the bridge's session-mode MCP tools
a2a_enroll, a2a_release, a2a_send and a2a_status (`__bridge-mcp
<home>/.loop/sessions/<slug>/<session-id> claude`; there is no ack tool).
All of them go through `src/loop/a2a-session-client.ts`, which enforces:

- **Run each session with only its own token.** The client reads only the
  acting supervisor's `tokenEnv`. If the environment also has another
  configured supervisor's token variable set (non-empty), it refuses and
  names the variables (never their values): `the environment also holds
  other supervisors' token variables (BOB_TOKEN); run each session with only
  ALICE_TOKEN set, or pass --allow-multi-token-env`. The fix is to start the
  session (tmux pane, Claude Code, shell) with only its own variable, for
  example `env -u BOB_TOKEN loop a2a ...`, or an env file per supervisor.
  `--allow-multi-token-env` on `loop a2a` is a deliberate human override
  for that one command, and even then only `--as`'s token is sent. The MCP
  tools have no override; the `--a2a-as` launch claim, the teardown release
  (logged, the lease lapses by its TTL) and `loop mailbox ack` refuse too.
- **The acting supervisor is never tool input.** In bridge session mode it
  is `supervisor:<slug>` of the session dir in the bridge's start argv (the
  dir `loop a2a enroll --kind claude-channel` prints), fixed when the bridge
  starts. No tool schema has an identity, token or takeover field, and a
  call that sends one (`as`, `from`, `supervisor_id`, `on_behalf_of`,
  `token_env`, `takeover`, ...) is refused before anything is read or sent.
  On the CLI it is `--as`, still required.
- **Takeover is a human CLI flag only.** a2a_enroll lost its `takeover`
  option; use `loop a2a enroll ... --takeover`. Enrolling a run whose
  manifest already names another `a2aSupervisorId` is refused (`the run is
  enrolled as supervisor:x; only an explicit --takeover renames it`) before
  the manifest is touched or a request is sent.
- **No forwarding.** A message's `from` (`harness.dev/from`) is always the
  acting identity; the client never relays a request, target or id for a
  caller beyond that identity, and a release refuses a lease recorded for
  another supervisor.
- **The token goes only to the config's server.** The server is the
  orchestration config's `origin` when it names one (RA1, below), else its
  loopback `hostname`/`port`; every request URL is
  checked against that origin before the token is attached (a path with
  `//`, a backslash, whitespace or control characters is refused), and
  redirects are refused. Ids from messages or tool input are validated as
  ids and never become a host.
- **A `LOOP_ORCHESTRATION_CONFIG` override must be trusted.** It must be a
  regular file (a symlink is judged by its target) owned by the current
  user and not group- or world-writable (`chmod 600` or `644`), else the
  client refuses with `LOOP_ORCHESTRATION_CONFIG is not owned by the
  current user`, `... is group- or world-writable` or `... is not a regular
  file`. The check runs on the descriptor that is read. The default
  `~/.loop/orchestration/config.json` is not checked by this rule.

### A2A V2 ACK refusals (ra1, 2026-10-11)

`loop a2a ack` (and `loop mailbox ack` for V2 envelopes) claims and then
acknowledges each workflow on the recipient route. A refusal names its
codes: `ack refused for <workflow-id> (acknowledge: <code>; claim: <code>)`.
Only codes from a fixed set are shown, and anything else reads `refused`.

- `assignment-denied`: this supervisor is not the message's recipient, or
  its endpoint is not reachable now. That means the lease was released and
  there is no mailbox, or the lease expired and the server does not observe
  the session live. An expired lease whose session is live is renewed on the
  spot, and a check that a renewal of the same lease raced is made once more,
  so the sweep's renewal timing does not refuse a live recipient.
- `delivery-not-recorded`, `not-claimed`: the recipient was early. It holds
  the message (a Claude session's pushed entry, a mailbox envelope) before
  the workflow recorded the delivery or the claim. Nothing is signalled, so
  the ACK waits these out with the same request ids for up to 120 s, at the
  server's `retryAfterMs` or a bounded backoff. Once the delivery's retry is
  due, the claim records the delivery itself. You see these codes only when
  the wait ran out; run the ack again.
- `lifecycle-command-refused`: the workflow refused the command (dead-lettered,
  cancelled, already acknowledged under other request ids, or an engine
  error).
- `unavailable`, `v2-unavailable`: the server or its V2 plane did not answer.

Tests: `recipient-api-client.test.ts`, `supervisor-message-v2-http.test.ts`,
`supervisor-message-v2-runtime.test.ts` (early claim and acknowledge on a
port that, like Temporal's, replays refusals),
`supervisor-message-v2-recipient-assignment.test.ts`,
`loop-orchestration-server-r9.test.ts` (renewal on demand), and the r9 e2e

them, the route's early code, the client's wait, the code allowlist, the
on-demand renewal and its liveness check, and the renewal-race recheck with
its epoch and revision conditions.

### RA1: origin policy and session tokens (claude/ra1-tokens-tls)

Nothing here exposes the server: it still binds exactly the configured
`hostname`. RA1 replaces four loopback-only checks with one policy
(`src/loop/orchestration-origin-policy.ts`) and adds session tokens
(`src/loop/orchestration-token-service.ts`). Static `tokenEnv` tokens keep
working unchanged as legacy.

- **Origin policy.** Plaintext only on a loopback IP literal: an `http:`
  origin must be `127.0.0.1` or `[::1]` (never `localhost`), and every
  binding `a2a-v2 init`'s ledger port is published on must be `127.0.0.1:`
  or `[::1]:`. Anything else is an `https:` origin (TLS terminated by
  Caddy). URLs with credentials, a query or a fragment are refused. Used by
  the server's config parser, the A2A client (`a2a-session-client.ts`), the
  recipient route client (`recipient-api-client.ts`) and the ledger check.
- **Config.** Three optional keys:
  - `origin`: where clients reach the server, for example
    `"https://loop.home.lab"`. The A2A client sends its token there instead
    of to `http://<hostname>:<port>`, and the agent card advertises it.
  - `tokens`: `{"signingKeyFile": "/abs/path/signing.pem"}`, an Ed25519
    PKCS#8 PEM in a regular 0600 file this user owns (not a symlink). The
    key is never inline. The store is `<stateDir>/tokens/token-store.json`
    (0600, directory 0700).
  - `supervisors[].role`: `{"role": "owner"|"operator"|"supervisor"|"worker",
    "repoKey": "...", "project": "..."}`. A role-bound address has a
    principal no other supervisor shares, and a repoKey/project has at most
    one `supervisor` address.
  - A `hostname` beyond loopback (`0.0.0.0`, a tailnet address) is refused
    unless the config also has an `https` origin and a `tokens` section.
- **Tokens.** EdDSA JWTs, 30 minutes, claims `sub` (session id), `repoKey`,
  `project`, `role`, `epoch`, `aud` (`loop-control`), `jti`, `iat`, `exp`.
  A session acts only as the address it enrolled as: the server maps the
  token subject to that address and its configured principal, so every
  downstream sender check binds to the token subject.
- **Host commands** (whoever reads the key is the owner already):
  - `loop orchestration token-keygen <config>` writes the configured key
    file (never overwrites one).
  - `loop orchestration token-code <config> <supervisor-id> --out <new-file>`
    writes a single-use, 10-minute enrollment code to a new 0600 file. The
    code is never printed.
  - `loop orchestration token-revoke <config> --session <id> | --jti <jti> |
    --epoch <supervisor-id>` revokes a session, denies one token until it
    would expire, or bumps the role epoch of that address's role and
    subtree (every earlier token of it stops verifying).
- **Routes** (`POST`, JSON, `cache-control: no-store`):
  `/api/v1/tokens/enroll` `{"code"}` (the code is the credential) answers
  `{data: {token, sessionId, expiresAt, audience, tokenType}}`;
  `/api/v1/tokens/refresh` (Bearer session token) issues a new token for a
  live, non-revoked session and denies the presented one;
  `/api/v1/tokens/enrollment-codes` `{"supervisorId"}` and
  `/api/v1/tokens/revoke` `{"sessionId"}|{"jti"}|{"epochFor"}` act as the
  verified session only. A static legacy token never mints, refreshes or
  revokes.
- **Grants by role subtree.** A role-bound sender is governed by its role,
  never widened by a configured grant: an owner may message anyone; a
  supervisor messages (and cancels) the workers of its own repoKey/project;
  a worker messages only its own subtree's supervisor; an operator messages
  supervisors. Within an allowed pair the sender receives and cancels, the
  recipient claims and acknowledges, either ticks, and a claimant must be
  the actor itself. Minting a code or revoking a session follows the same
  subtree (owner: any; supervisor: its workers; any session: itself);
  epoch bumps are owner or host only. A sender without a role keeps its
  configured grants exactly as before.

## Governess beat (gov-6)

The governess beat runs as a Temporal workflow. Its history is the authoritative,
ordered event log, and the JSONL control journal is a read model projected out of
it.

- Workflow type: `governess-beat.v1`
- Workflow id: `governess-beat:v2:<repoId>:<runId>:<taskQueue>` since fix7
  (`src/loop/governess-beat-identity.ts`). Before fix7 it was
  `governess-beat:<runId>`, which collided across repos; see
  "Temporal journal: SUSPENDED, fix7, and re-enabling it" below before setting
  any `LOOP_GOVERNESS_TEMPORAL_*` variable.
- Namespace: `harness`
- Definition: `src/loop/governess-beat-workflow.ts`
- Reducer shared with the JSONL writer: `src/loop/governess-journal-core.ts`

### Turning the Temporal journal on (gov-6 v3)

> SUSPENDED since 2026-09-19 (P1 cross-repo workflow-id collision). Do not set
> these variables with any build that predates fix7. The procedure that
> replaces the block below is "Temporal journal: SUSPENDED, fix7, and
> re-enabling it". Since fix8 the journal is on by default without any
> variable; see "Defaults on (fix8, 2026-10-11)" at the top.

The live governess writes its journal through the beat workflow only when both
variables are set in the governess pane's environment; with neither set it keeps
the file journal and never loads the Temporal SDK. Setting only one is an error.

```bash
LOOP_GOVERNESS_TEMPORAL_ADDRESS=192.168.1.18:7233
LOOP_GOVERNESS_TEMPORAL_NAMESPACE=harness
LOOP_GOVERNESS_TEMPORAL_TASK_QUEUE=loop-governess   # optional, this is the default
```

- Authority: when both exist, Temporal history is authoritative. The run-dir
  `governess-control.jsonl` stays the synchronous write-ahead copy the governess
  fences against; every record is then signalled (`append_record`) to the
  run's beat execution in order: by exact run id when it is running, via
  `signalWithStart` when it is not, and only after its task queue and owner
  memo prove it is this run's (fix7).
- Recovery: on every governess start the file is reconciled from history before
  the epoch is acquired. History wins a disagreement at a held sequence; a file
  that is missing or behind is rewritten from history; a file tail newer than
  history (records the dead pane never signalled) is replayed into history. The
  outcome is logged as `journal-temporal-recovered` in `governess.jsonl`.
- Recovery reads raw history, so it needs the server but not a worker. It waits
  for a settled history (no workflow task in flight, event count stable),
  because Temporal buffers signals that arrive during a workflow task.
- A failed signal is logged as `journal-temporal-append-failed`; later records
  queue behind it and the next start's recovery replays them.
- Live proof: `bun run scripts/governess-temporal-live-proof.ts` with the two
  variables set. It runs its own worker on a private task queue and terminates
  its proof workflow when done.

### Temporal journal: SUSPENDED, fix7, and re-enabling it

Written 2026-10-10 on claude/fix7-governess-temporal-journal (from
claude/fix-integration-r6-2026-10-09 at c16636fc). Not merged, not installed,
nothing enabled. Every step below that sets a variable, terminates an
execution or installs a binary is an operator decision; the listing command is
the only one that talks to the live server, and it only reads.

#### What collided (the 2026-09-19 P1)

- Id derivation, every build from gov-6 (f0e6d158) to the r6 base:
  `governessBeatWorkflowId(runId)` = `governess-beat:${runId}`
  (src/loop/governess-beat-workflow.ts). Run ids are per-repo integers
  (`reserveRunStorage`, run-state.ts), so two repos that journal into one
  namespace derive the same id for their run 29.
- Write: `appendRecord` used `signalWithStart`, which signals whatever
  execution holds the id, and wrote the owner memo (`loopRepoId`, since
  7b5ccdbf; ec185ba1, the build first installed with the journal on as
  cc8d978c, wrote none) only when it created one. Repo B's records went into
  repo A's history.
- Read: recovery read `getHandle(governess-beat:<runId>)` with no owner check
  and history wins every disagreement, so repo B's governess rewrote its own
  file journal from repo A's records (reproduced by the test "isolation: two
  repos with the same run id ..." before the fix: B recovered A's records).
- Only the close path checked the memo, and it let a run's own governess close
  an execution with no memo.

The r6 deployment discriminator does not cover governess beats. It is the V2
message id format (`supervisor-message-workflow:v2:deployment:<sha256>`) plus
`TemporalWorkflowPort.#owned`, which refuses an execution on another task
queue for every port call (temporal-workflow-port.ts). The governess journal
and the beat close never go through the port: they call `WorkflowClient`
directly (`signalWithStart`, `getHandle(id).describe/fetchHistory/terminate`),
and the beat id carries no repo and no deployment.

#### What fix7 changes

- Id: `governess-beat:v2:<repoId>:<runId>:<taskQueue>`. The repo id is the
  run manifest's (`<repo name>-<12 hex of the git common dir>`), the task
  queue is `LOOP_GOVERNESS_TEMPORAL_TASK_QUEUE` (default `loop-governess`),
  which is the deployment discriminator the V2 port uses. No legacy id
  (`governess-beat:<runId>`, one colon, run ids cannot hold one) can equal an
  owned one.
- Memo on creation: `loopBeatIdFormat` `v2`, `loopRepoId`, `loopRunId`,
  `loopTaskQueue`.
- Every call verifies before it acts (governess-temporal-journal.ts
  `appendOwned`/`readOwned`, governess-beat-close.ts `closeOwnedExecution`):
  describe; refuse unless the execution runs on this task queue and its memo
  names this repo, run and queue; then address the exact run id that was
  verified (signal, history read, terminate). A refusal in the journal throws
  `GovernessBeatForeignJournalError` ("... is not this run's journal"), so a
  governess start fails loudly instead of adopting a foreign journal. A run
  that `signalWithStart` creates is described again and verified.
- Legacy ids during the transition: the journal never reads or writes one. Its
  history may hold another repo's records, so the run's file journal (always
  complete: it is the write-ahead copy, archive included) is backfilled into
  the new id on the first start under fix7. The close path still closes a
  legacy execution, only when it runs on this task queue and its memo names
  this repo; one with no memo is `refused-unowned` for every caller, including
  the run's own governess (that exception is removed). `closeGovernessBeatWorkflow`
  reports it as `legacy` beside the owned outcome; reconcile counts both.
- The workflow bundle is unchanged (identical modules to the r6 base's
  committed bundle; the committed generated file is untouched), so no replay
  or handoff changes. Inside a new execution the beat's start result still
  reads `governess-beat:<runId>`: a label in its state, not its id.
- `loop governess history <run-id>` prints `workflowId` (owned, for this repo
  and the configured or default queue), `legacyWorkflowId` and `taskQueue`.

#### Limits

- Ownership rests on the task queue and the memo. Search attributes are not
  used (they need namespace registration). Anyone who can write to the
  namespace can forge a memo; the check separates cooperating repos and
  deployments, it is not access control.
- A racing creator under the same owned id (possible only with the same repo
  id, run id and queue) is detected after `signalWithStart` and reported, but
  that one signal has already landed.
- A run resumed after its execution was terminated journals into a new run of
  the same id (unchanged from gov-6): recovery then reads only the new run.
- `expect(promise).rejects` on a Temporal client call stalled the gRPC client
  for about 45 s per call under bun 1.4.2 in these tests; the new tests await
  the call directly (`refusal()`).

### One workflow per run, not per seat

The journal's invariants are run-global. The idempotency fence, the monotonic
`sequence` counter, and observation-stream dedupe all key across every seat in a
run. Splitting per seat would shard that fence into independent counters, giving
duplicate sequence numbers with no total order and letting the same idempotency
key pass twice on two different seats. Seat identity travels instead as the
record's `agent` field and inside `observationStream`.

### Inspecting a run

```
loop governess history <run-id>
```

Prints the exported journal read model together with the workflow id and type
that own it. The other governess utility commands are unchanged:

```
loop governess <doctor|replay|explain|history|signals|recover-control-plane> <run-id> [control-id]
```

### Audit contract: metadata only

History carries no prompt bodies.

- Effectful controls cross the boundary as `payloadHash`. The beat workflow
  rejects a `prepare_control` signal that carries a `payload` field, so a body
  cannot reach history even if a caller is careless.
- `payload` is retained only for `observe-runtime`, which is runtime output
  rather than a prompt, and is what lets replay reconstruct decisions.

Callers must hash before signalling. `governess-journal-core.ts` deliberately
imports no Node built-ins — a `node:crypto` import there breaks the webpack
workflow bundle and would drag hashing into the workflow sandbox.

### Changing the beat workflow

The orchestration server registers workflows through the shared bundle, so after
editing `src/loop/temporal-workflow.ts` or any module it pulls in you must
regenerate the bundle or the server keeps running the old code:

```
bun run build:temporal-workflow
```

`LOOP_ORCHESTRATION_WORKFLOW_TYPES` in `src/loop/loop-orchestration-server.ts`
is the declared surface of that bundle.

### Workflow id formats

- Legacy: `supervisor-message-workflow:v2:<sha256>`, byte for byte the id the
  pre-discriminator build (40097564) derives (supervisor-message-v2-contract.ts:773-780).
  Rows carry `deployment` NULL.
- Deployment: `supervisor-message-workflow:v2:deployment:<sha256>`, scoped to
  the deployment, which is the host's Temporal task queue
  (supervisor-message-v2-contract.ts:751-763; supervisor-a2a-v2-service.ts:728-733).

In either mode a host reads, recovers and deduplicates both formats: a dedupe
key already recorded under one id keeps it (supervisor-message-v2-delivery-ledger.ts:406-430).

The database records the format in `loop_supervisor_message_v2_schema_marker`,
row `workflow-id-format.v1`, columns `value` and `build_id`. A BEFORE INSERT
trigger, `loop_supervisor_message_v2_start_intent_format_guard_v1`, refuses for
every writer (older builds included) a start intent in any other format, and a
legacy intent for a message already held under a deployment id
(supervisor-message-v2-delivery-ledger.ts:77-101, 513-562).

Every V2 workflow port call checks that the execution runs on this host's
task queue and refuses one on another queue as `WorkflowError (conflict)`
(src/loop/temporal-workflow-port.ts:199-221). That check works in both
formats. In legacy format it cannot refuse a start whose execution does not
exist yet, so hosts on different task queues that share one ledger database
are not isolated (decision 6 is off) until every one of them writes
`"deployment"`.

Start log lines, one per start (supervisor-a2a-v2-service.ts:613-626):

- `A2A V2 workflow ids: legacy format. The deployment discriminator is off: every host sharing this ledger database recovers and deduplicates the others' messages. Set a2aV2.workflowIdFormat "deployment" on every such host once all of them run a build that supports it`
- `A2A V2 workflow ids: deployment format, scoped to this host's task queue`

Startup refusals over the format (supervisor-message-v2-delivery-ledger.ts:526,
540). The service prints them verbatim after "Supervisor A2A V2 service
initialization failed at delivery-ledger: " (supervisor-a2a-v2-service.ts:934-937):

- `V2 delivery ledger records workflow id format "<format>" (written by build <build>), which this build does not support; it supports "legacy" and "deployment". Run a build that supports the recorded format`
- `V2 delivery ledger cannot return to legacy workflow ids: <n> deployment-format start intents have no terminal outcome. Keep a2aV2.workflowIdFormat "deployment" until they settle`

A write refused by the trigger raises: `V2 delivery ledger writes "<recorded>"
workflow ids (recorded by build <build>); a "<written>" start intent is
refused. Every host sharing this ledger database must run a build that
supports the recorded format, with the same a2aV2.workflowIdFormat`
(supervisor-message-v2-delivery-ledger.ts:86-89).

### Result graph ids, the result-graph route and the CLI

A message's result graph id is `supervisor-result-graph:v3:<hmac-sha256>`:
HMAC-SHA256 under the host key over ("supervisor-result-graph", "v3", tenant,
principal, messageWorkflowId), each field length-prefixed and NUL-terminated
(supervisor-message-v2-contract.ts:782-856). The retired unkeyed id
`supervisor-result-graph:v2:<sha256>` is still recognised for bindings
recorded before the key; no new binding may name one
(supervisor-message-v2-delivery-ledger.ts:361-371, 741-768).

Compute an id offline, for a `resultArtifacts` entry:

```
loop orchestration result-graph-id <config-path> <message-workflow-id>
```

It reads the config's `a2aV2` tenant, control principal and key variable,
prints only the id, and never starts the server
(src/loop/orchestration-command.ts:5-7, 36-48, 79-89;
loop-orchestration-server.ts:1544-1566). It fails with "orchestration config
has no a2aV2 route" or "orchestration a2aV2 has no resultGraphKeyEnv" when
those are missing.

Start a message's result graph over HTTP, as the control principal (a2aV2
`principal`):

```
POST <a2aV2.routePath>/result-graph
{"input": <task-graph.v1 input>, "messageWorkflowId": "...", "requestId": "..."}
```

The host checks that the message's start intent is recorded in the route's
scope, derives the graph id under its key and starts `task-graph.v1` under it
(supervisor-a2a-v2-service.ts:492-516). Success is 200 with
`{"schema": "supervisor-result-graph-start-receipt.v1", "messageWorkflowId", "graphWorkflowId", "created"}`;
a refused start is 409 `{"code": "result-graph-start-refused"}` with no cause
(src/loop/a2a-supervisor-assignment-http.ts:204-268). The route is mounted at
`<routePath>/result-graph` (loop-orchestration-server.ts:1389-1392).

The old route refuses these ids. `POST /api/v1/task-graphs/start` with a
`workflowId` starting `supervisor-result-graph:` returns 403 with
`error.code` `"result-graph-id-reserved"`, unchanged since r3, and since r4
also `error.message` and `error.replacement`:
`{"method": "POST", "route": "<routePath>/result-graph" or null when the server mounts no A2A V2 route, "body": ["input", "messageWorkflowId", "requestId"], "resultGraphIdCommand": "loop orchestration result-graph-id <config-path> <message-workflow-id>"}`
(src/loop/supervisor-orchestration-http.ts:62-86, 256-261). Ids outside the
prefix start as before. Operator scripts that started result graphs through
task-graphs/start must move to the result-graph route.
`TemporalSupervisorRuntimeHost.httpHandler(authenticator, options?)` takes an
optional `{resultGraphRoutePath?: string}`; one-argument callers are unchanged
(src/loop/temporal-supervisor-runtime.ts:325-334).

Bind a result (unchanged route, keyed check since r3): `POST
<routePath>/assignment` with {a2aTaskId, graphTaskId, graphWorkflowId,
messageWorkflowId, recipient}. The graph must equal the keyed id of the
message and be listed in `resultArtifacts`. Any refusal is 409
`{"code": "assignment-refused"}` (a2a-supervisor-assignment-http.ts:127-195;
supervisor-a2a-v2-service.ts:419-490).

```
{
  "schema": "loop-orchestration-health.v1",
  "state": "ready" | "unavailable",
  "notEnrolledCount": <n>,
  "a2aV2NotEnrolledDeferral": {"boundMs", "deferredDeliveries", "notEnrolledFailures", "recipientsDeferred"},
  "a2aV2ReadinessOutage": {"boundMs", "deferredDeliveries", "outageFailures", "recipientsDeferred"}

```

The two `a2aV2*` blocks appear only when an A2A V2 service is mounted.
`notEnrolledCount` is always supplied by the server (loop-orchestration-server.ts:1725-1731).
`state` ignores both deferrals. Counters are cumulative since process start;
each `recipientsDeferred` is a current count
(supervisor-message-v2-runtime.ts:114-131, 244-259, 310-321, 408-420). On r3
the body carried `notEnrolled` with seat ids instead of `notEnrolledCount`; a
consumer reading `notEnrolled` must read `notEnrolledCount` or the
authenticated status below.

Authenticated `GET <routePath>/assignment`, control principal only, returns
`{"schema": "supervisor-result-assignment-status.v1", "notEnrolled": [seat ids], "readinessOutage": [recipient ids], "unpublishable": [...]}`
(a2a-supervisor-assignment-http.ts:66-108; supervisor-a2a-v2-service.ts:628-664).
`unpublishable` lists this tenant's bindings recorded before graphs were
derived (`body-chosen-graph`) or unreadable (`malformed`). On r4 and the
round-5 base it does not list a binding stranded by a key change (see
rotation below); on claude/fix5-key-rotation it does, and the GET also
carries `underPreviousResultGraphKey` (see "Result graph key rotation
(claude/fix5-key-rotation)").

On the round-5 base the same GET also carries `"recoveryQuarantine": [...]`:
this tenant's records an operator quarantined from recovery, each as
`{"at", "by", "reason", "recipient", "workflowId"}` (round-5 base:
a2a-supervisor-assignment-http.ts:72-128; supervisor-a2a-v2-service.ts:633-675).
A quarantine never appears on /healthz, not even as a count. (Owner decision
2026-10-09, Q2: unauthenticated /healthz carries no seat ids. A quarantine
count there was not part of that decision; none is added.) A failing read of
any section answers 503 `{"code": "status-unavailable"}` with no cause.

Readiness outage semantics (d6392ce9, supervisor-message-v2-runtime.ts:145-171):
the bound is measured from the first failure a delivery observed for that
recipient. An outage ends when the store answers for that recipient, or when
no delivery observed it for 2 hours and no message it failed still waits on
its retry. `recipientsDeferred` and the `readinessOutage` list include only
recipients observed in an outage within the last 2 hours. A later, separate
outage gets its own bound. State is in memory, so a restart starts the bound
again. Log lines: `V2 delivery to <recipient> deferred: session readiness store is unavailable`,
`... still deferred after <bound>ms: the readiness store outage now fails delivery attempts`,
`... resumed after <ms>ms: session readiness store answered`
(supervisor-message-v2-runtime.ts:196-237).

Not-enrolled deferral (f3f8c2e1): a peer seat that is not running or not
reachable degrades that seat alone at start; the configured recipient's own
failure, or any other peer failure, still refuses start
(loop-orchestration-server.ts:936-978, 1053-1077). Since the fix8 critic fix
no enrollment failure refuses start: every seat, the configured recipient
included, whatever the cause, is degraded alone and retried by the sweep.
Log lines:
`orchestration A2A V2 session enrollment failed for <seat>: <cause>` and
`orchestration A2A V2 session enrollment recovered for <seat>`
(loop-orchestration-server.ts:1228-1247); `V2 delivery to <recipient> deferred: recipient session is not enrolled`,
`... still deferred after <bound>ms not enrolled: delivery attempts now fail`,
`... resumed after <ms>ms: recipient session is enrolled and ready`
(supervisor-message-v2-runtime.ts:365-406).

### Recovery at start (decision 7)

Service-start recovery skips only a record whose id is held by an execution
this deployment does not own, logging `V2 recovery skipped workflow <id> for <recipient>: WorkflowError (conflict): ...`.
Any other per-record failure, or a failure of the whole sweep, refuses
startup after every other record was recovered
(supervisor-message-v2-runtime.ts:543-556, 640-662, 735-740). The periodic
sweep retries a failing record with backoff min(interval x 2^(n-1), 10 min)
and logs each transition (supervisor-message-v2-runtime.ts:697-733).

Two limits on r4, both fixed on the round-5 base (next subsection):

- The refusal reaches the operator only as `Supervisor A2A V2 service initialization failed at runtime-host (unclassified)`.
  `SupervisorMessageV2RecoveryStartupError` names every failing record, but it
  is not on the service's list of reportable error names and the runner does
  not log it (supervisor-a2a-v2-service.ts:316-327, 939-942;
  supervisor-message-v2-runtime.ts:652-661). r4 has no way to start past such
  a record. On r4, find the record by its own symptom (database or Temporal
  error) and repair it before restarting.
- A conflict at start counts as foreign whatever its cause. That includes an
  execution of another workflow type on this host's own task queue: the port
  raises `WorkflowError (conflict): workflow <id> already exists as <type>`
  (temporal-workflow-port.ts:150-156), and recovery skips it. On r4 the test
  "the orchestration server starts when a recorded V2 workflow ID is held by
  a foreign execution" (tests/loop/loop-orchestration-server-postgres.test.ts)
  pins that skip for a running `supervisor-message.v1` execution on the same
  queue.

### Recovery quarantine (round-5 base)

On the round-5 base (merge 0ea648f9 of claude/fix4-recovery-escape-path,
26f91ac5), recovery at start changes in three ways. Paths below are at the
round-5 base.

- Only an execution on another task queue is foreign. The port raises it as
  `WorkflowForeignExecutionError`, still a `WorkflowError (conflict)` with
  the message `workflow <id> belongs to another task queue`
  (temporal-workflow-port.ts; workflow-port.ts), and recovery skips only that
  (supervisor-message-v2-runtime.ts:503-511). Another workflow type under a
  recorded id on this host's own queue is a failure: running, the port's
  start refuses the type; closed, the coordinator refuses any status answer
  that is not a `supervisor-message-status.v2` projection, so the other
  type's state is never recorded as this message's terminal outcome
  (supervisor-message-v2-runtime.ts:1552-1564).
- A refused start names each failing record and the exact command that
  quarantines it, and the runner logs it as well
  (supervisor-message-v2-runtime.ts:543-567, 777-787):
  `V2 initial recovery failed for <n> recorded start(s): workflow <id> for <recipient>: <error> [to start without it: loop orchestration v2-quarantine <config-path> <id> --reason '<why>']`.
  The service reports the class:
  `Supervisor A2A V2 service initialization failed at runtime-host (SupervisorMessageV2RecoveryStartupError)`
  (supervisor-a2a-v2-service.ts:320-331). A start intent row that cannot be
  read at all fails the whole sweep; at start it is refused the same way, by
  its workflow id, with the recipient shown as `an unreadable recipient`
  (supervisor-message-v2-runtime.ts:740-757).
- An operator can quarantine such a record explicitly and durably. Recovery
  then leaves it alone, does not retry it, and logs at every start
  (supervisor-message-v2-runtime.ts:789-818):
  `V2 recovery QUARANTINED workflow <id> for <recipient>: skipped until released (quarantined by <by> at <at>: <reason>); release it with: loop orchestration v2-quarantine-release <config-path> <id> --reason '<why>'`.
  A release is logged once, `V2 recovery quarantine of workflow <id> for <recipient> was released; recovering it again`,
  and the record is recovered as any other from the next sweep.

Commands (src/loop/orchestration-command.ts:7-16, 43-111; loop-orchestration-server.ts:1570-1664):

```
loop orchestration v2-quarantine <config-path> <workflow-id> --reason <text> [--by <operator>]
loop orchestration v2-quarantine-release <config-path> <workflow-id> --reason <text> [--by <operator>]
loop orchestration v2-quarantine-list <config-path>
```

- `--by` defaults to the operating-system user running the command. `by` is
  1-200 characters and `reason` 1-1000, with no control characters.
- The command reads the config, takes the database URL from the environment
  variable named by `a2aV2.databaseUrlEnv`, and opens this deployment's
  ledger (its `taskQueue`) as the server does: the config's `buildId` and
  `a2aV2.workflowIdFormat`. Every one of the three commands, the list
  included, runs the server's full migrations: the additive DDL, the format
  marker write and, in legacy format, the legacy-id backfill. So on a
  database with no format marker it records what the server's first start
  would. Do not run any of them with a config whose `workflowIdFormat`
  differs from the one the running hosts use: like a server start, it would
  record the config's format, and the guard trigger would then refuse the
  running hosts' new start intents. Use the running hosts' own config. It
  never starts the server. Whether these commands should leave the format
  alone is an open owner question.
- Output names workflow ids, recipient, who, when and why, never the database
  URL: `quarantined <id> for <recipient> by <by> at <at>: <reason>`,
  `already quarantined ...` (the first quarantine stands, unchanged),
  `released <id> for <recipient> (quarantined by <by> at <at>: <reason>)`,
  and for the list `<id> for <recipient> quarantined by <by> at <at>: <reason>`
  or `no quarantined V2 recovery records`.
- Refusals: `V2 workflow <id> has no start intent recorded by this deployment`
  (another deployment's record, or none), `V2 workflow <id> already has a
  terminal outcome; recovery leaves it alone`, `V2 workflow <id> is not
  quarantined` (release), `missing orchestration A2A V2 database environment
  <VAR>`, and `orchestration A2A V2 ledger is unavailable` for any connection
  or migration failure (no cause, which may carry credentials). A workflow id
  format refusal is printed as `orchestration A2A V2 ledger refused: ` followed
  by the exact ledger message listed under "Workflow id formats".
- Only an open start intent of this deployment, its own or a legacy one
  (`deployment` NULL), can be quarantined, readable or not. A legacy row is
  recovered by every deployment sharing the database, and each deployment
  quarantines it separately.

Quarantine and workflow id formats: a quarantine is not a terminal outcome,
and recovery never settles a quarantined record. A quarantined
deployment-format record therefore counts as unsettled, and every start with
`a2aV2.workflowIdFormat` `"legacy"` (or none) is refused with "cannot return
to legacy workflow ids" until the record is released and recovery records
its outcome; releasing it is not enough. No outcome can be recorded by hand
(owner decision 2026-10-09: no hand-recorded terminal outcomes). So while a
deployment-format record is quarantined, a return to legacy ids, including a
rollback to the legacy-write default, is blocked. Plan the release before
planning that rollback.

Storage: table `loop_supervisor_message_v2_recovery_quarantine`, one active
row per (workflow id, deployment); a release keeps the row with who, when and
why as history (supervisor-message-v2-delivery-ledger.ts:566-584, 1015-1110).
Status: the authenticated assignment GET lists this tenant's quarantines (see
"Health and status surfaces"). A deployment without an assignment route has
only the start-time log lines and `v2-quarantine-list`, which needs the

one is durably recorded as `terminated` from the other type's status. That
record is not undone by upgrading again. Before rolling back, resolve each
same-queue conflict the round-5 base reported.

### What existing rows and bindings do on upgrade

All migrations run in `migrate()` on the first start and are additive
(supervisor-message-v2-delivery-ledger.ts:432-496):

- Start intents written before the discriminator keep their legacy id with
  `deployment` NULL. Nothing is rewritten or backfilled.
- `terminal_outcome` is not backfilled (decision 5). Existing rows read NULL,
  meaning no outcome observed. A closed execution Temporal still holds gets
  its marker on the next recovery sweep. An execution purged before the
  marker existed, with no completed delivery, cannot be told from a lost
  start and is restarted.
- A database migrated by the 3f7a70f2 build: inside one transaction holding
  ACCESS EXCLUSIVE on `loop_supervisor_message_v2_start_intent`, migrate
  decides whether the `terminal_outcome` CHECK is current. It is current when
  one exists, no CHECK allows `'completed'`, and every CHECK allows every
  current outcome; a CHECK widened to a superset of the current list (for
  example by a newer build) is therefore current. A current CHECK is left in
  place: the step takes the lock briefly and changes nothing. Otherwise (the
  3f7a70f2 CHECK, a missing CHECK, or one missing a current outcome) every
  `terminal_outcome` CHECK is dropped, stored `'completed'` is rewritten to
  `'acknowledged'`, and the CHECK
  `loop_supervisor_message_v2_start_intent_terminal_outcome_check` over
  ('acknowledged', 'canceled', 'dead-lettered', 'exhausted', 'terminated') is
  added. Only in that replacement case can migrate fail: if a stored value is
  outside the current list, adding the CHECK fails and so does migrate
  (supervisor-message-v2-delivery-ledger.ts:590-632).
- Result bindings recorded under the unkeyed v2 graph of their own message
  are reserved once (marker `result-graph-task-backfill.v1`), keep publishing
  and stay immutable. Bindings that named a body-chosen graph, or cannot be
  read, are recorded once in `loop_supervisor_message_v2_unpublishable_result_binding`,
  logged at every start as `A2A V2 result binding will never publish (<reason>): tenant <T> message <M> A2A task <A>; re-bind it to its message-derived result graph`,
  and listed by the authenticated assignment GET. Re-binding the message to
  its keyed graph clears the entry
  (supervisor-message-v2-delivery-ledger.ts:634-699, 836-846;
  supervisor-a2a-v2-service.ts:590-604).
- Temporal graphs already started under a v2 id keep running; nothing is
  renamed.
- A database written by the r3 build has deployment-format rows and no
  format marker. It defaults to `"legacy"`, so start is refused with the
  "cannot return to legacy" message until `"deployment"` is set or its rows
  settle.
- Session receipts are not rewritten. Each seat's backlog is pruned at that
  seat's first rebind. The first migrate builds two seat indexes with plain
  CREATE INDEX, which blocks receipt writes while each index builds
  (supervisor-session-v2.ts:634-647).
- Round-5 base only: migrate also creates the empty
  `loop_supervisor_message_v2_recovery_quarantine` table and its partial
  unique index (round-5 base: supervisor-message-v2-delivery-ledger.ts:566-584).
  Nothing existing is rewritten.

execution until something terminates it; a governess beat never ends. A
worker on a new bundle rebuilds each execution's state by replaying its

   `cp -p ~/.loop/orchestration/config.json ~/.loop/orchestration/config.json.pre-v2-<UTC>`.

   `grep -c '^LOOP_BIN=' ~/.config/loop/orchestration.env` prints 1. The
   upgrade rewrites that line; a rollback rewrites it back.
4. Back up the config's `stateDir` (`threads.jsonl`, `governance.jsonl`)
   and each supervisor's mailbox file and cursor. The V2 line reads and
   writes them with the same code as 455ccc32: supervisor-thread-store.ts,
   supervisor-message-governance.ts, supervisor-mailbox-delivery.ts,
   supervisor-mailbox-cursor.ts, supervisor-bridge-consumption.ts and
   supervisor-deadline-driver.ts have the same blob at both, and
   supervisor-mailbox-consumption.ts differs only in comment text
   (`git diff 455ccc32 <V2 head>`: +8/-2, all inside one doc comment).
   Two files that touch the same state do differ (checked 2026-10-09,
   455ccc32 against r5 integration 9b3dca36; added because this item used
   to list only the files that match):
   - bridge-store.ts (blob 1aff02cb at 455ccc32, 68848f7d at 9b3dca36),
     with bridge-supervisor-message-delivery.ts, bridge-runtime.ts and
     bridge.ts. These write each run's `bridge.jsonl`, the queue a V1
     message to a supervisor with a `manifestPath` goes through. The
     record format is unchanged; the enqueue is not. The V2 line keys a
     supervisor delivery `supervisor-delivery:<workflowId>` and deduplicates
     it against the run's whole bridge history, not only pending messages,
     and reuses an earlier enqueue of the same message instead of adding
     another; 455ccc32 keys each attempt by its idempotency key and
     deduplicates pending messages only. Every keyed enqueue on the V2 line
     holds a claim file `<runDir>/bridge-dedupe-claims/<sha256>.lock`
     (0600, created with exclusive create, holding `<pid>:<uuid>`) for the
     length of the enqueue, removes it when the enqueue returns or throws,
     and answers `deferred` while the file exists; 455ccc32 has no claim
     files and ignores the directory. Up to r5 integration (9b3dca36)
     nothing recovers a stale claim: no code checks the pid or the
     file's age, so a process that dies mid-enqueue (a crash, `kill -9`,
     a restart that lands inside the enqueue) leaves the file behind, and
     every later enqueue of that
     message, same source, target and key, answers `deferred` until
     someone removes it. Supervisor delivery treats `deferred` as a
     transient failure, so that message is retried but not queued while
     the file exists (bridge-store.ts `acquireBridgeDedupeClaim` and
     `enqueueBridgeMessage`, bridge-supervisor-message-delivery.ts at
     9b3dca36; reproduced 2026-10-09 in a scratch run directory: a claim
     acquired and never released, three enqueues under its key all
     `deferred`, another key `queued`). Pre-existing on the V2 line up to
     r5 integration. Since claude/fix6-hygiene (6f560720, merged on r6
     integration, claude/fix-integration-r6-2026-10-09), an enqueue that
     finds a claim reclaims it only when its owner pid is not running, or
     is running but started after the claim was written (a reused pid); a
     claim whose owner is alive with an unknown or not later start time,
     or whose owner token cannot be parsed, is never reclaimed and still
     answers `deferred` (bridge-store.ts, pid-ownership.ts
     `pidCanStillOwnRun`; tests/loop/bridge-dedupe-claim-reclaim.test.ts).
     Earlier V2 builds never reclaim. So before an upgrade, after it, and
     before and after any rollback or roll forward, list
     `bridge-dedupe-claims/` in the run directory of every supervisor
     with a `manifestPath`, and of any
     run whose own processes run a V2-line build (governess controls and
     the bridge tool's `dedupe_key` take claims too). With every process
     that writes that run's bridge stopped, any file there is stale. While
     they run, a file whose pid (the text before the first `:`) is not a
     running process (`ps -p <pid>`) is stale; a reused pid can make a
     stale file look live, so stop the writers when in doubt. Remove only
     stale files, and record what you removed. By code reading, the live
     config has no `manifestPath` supervisor, so this path is idle there
     until an `a2aV2` recipient is added (item 6). Back up, with the state
     above, the run directory (`bridge.jsonl`) of any supervisor that has a

### Result graph key rotation on r4

r4 holds one key and has no previous-key support. Rotating the key changes
every v3 id. Verified at the ledger level on 2026-10-06 with a throwaway test
(not committed) on real PostgreSQL, and by the committed test "no new binding
may name an unkeyed v2 graph, and a ledger without the key binds nothing":

- A binding recorded under the old key stops publishing under the new key.
  Nothing reports it: it is not in the unpublishable table, the start log or
  the assignment GET.
- Re-binding the same A2A task to its new-key graph replaces the old binding,
  and it publishes again. A host still holding the old key then no longer
  publishes it.

Procedure, if a rotation cannot wait for claude/fix5-key-rotation:

1. Drain: wait until every bound result has been published, so no binding is
   pending under the old key. r4 offers no listing of keyed bindings; check
   the A2A tasks you bound.
2. Put the new key in the secret store (a new variable name, or the same
   one), update `resultGraphKeyEnv` if the name changed, and recompute every
   `resultArtifacts` `graphWorkflowId` with `loop orchestration
   result-graph-id`. Old v3 ids still pass config parsing, so startup does not
   catch a stale entry.
3. Restart. For any message still pending under the old key, start its graph
   again with `POST <routePath>/result-graph`, add the returned
   `graphWorkflowId` to `resultArtifacts`, restart, and re-POST the
   assignment with it. The old graph's Temporal execution keeps running.

### Result graph key rotation (claude/fix5-key-rotation)

Not on r4 or the round-5 base; on r5 integration (merge 8e965197). Verified
on 2026-10-07 by tests/loop/supervisor-a2a-result-key-rotation.test.ts (18
tests; 20 with the two settled-check tests claude/fix6-runbook-tests adds)
on real PostgreSQL 17, and loop-orchestration-server-postgres "the orchestration
server holds its configured previous result graph keys" with Temporal.

What a host does with its keys:

- New bindings and result graphs are derived under the primary key
  (`resultGraphKeyEnv`) only. Nothing new is bound under a previous key: a
  bind naming a graph derived under one is refused, 409
  `{"code": "result-graph-under-previous-key"}` (a2a-supervisor-assignment-http.ts:71-77),
  except an exact retry of the binding already recorded while it still holds
  its graph task (supervisor-message-v2-delivery-ledger.ts:1371-1418).
- A binding derived under a previous key still publishes. A binding derived
  under a key the host does not hold is refused on publish with an error
  naming the key's fingerprint, and reported (`unknown-result-graph-key`).
- Each binding records the fingerprint of its key
  (`rgk:` + 16 hex digits, not reversible) and the deployment (task queue)
  that recorded it, in the additive column `bound_by_deployment`
  (supervisor-message-v2-delivery-ledger.ts:1179-1183).
- `loop orchestration result-graph-key-fingerprints <config-path>` prints
  `<ENV> <primary|previous> <fingerprint>` per configured key, never a key
  (loop-orchestration-server.ts:1650-1675). Use it to match a fingerprint in
  a log line or listing to a variable.

Whose bindings a host classifies (round-4 major 1). Keys belong to a
deployment, so a host classifies, lists and reports only its own
deployment's bindings, never those of another deployment sharing the ledger
database (supervisor-message-v2-delivery-ledger.ts:626-661):

- a binding recorded by this build belongs to the deployment that recorded
  it;
- a binding an older build recorded names no deployment and belongs to its
  message's owner: a deployment-format message (id
  `supervisor-message-workflow:v2:deployment:...`) to the deployment its
  start intent names; a legacy message to every deployment, as for
  recovery;
- the start report and the authenticated GET are further limited to the
  host's route tenant (supervisor-a2a-v2-service.ts:676-700). The start
  report of body-chosen and lost-reservation bindings is now limited to the
  route tenant too; before, a host reported every tenant's.

Limit: a legacy binding recorded by an older build, of the host's own
tenant, cannot be told apart from one under a key this deployment removed,
so it is reported by every deployment that shares the database and serves
that tenant (test "with legacy workflow ids, whose messages name no
deployment, ..."). Bindings recorded by this build are not affected.

When a binding settles (round-4 major 2). A binding needs no key any more
once its result was published (its A2A task holds the message's
`accepted:<messageWorkflowId>` artifact) or its A2A task ended without a
result (failed, canceled or rejected), since publication is then refused
forever. A missing task, a COMPLETED task that does not hold the message's
accepted artifact, or a task-store read that fails, counts as not settled,
so nothing is hidden (supervisor-a2a-v2-service.ts:644-673;
supervisor-message-v2-delivery-ledger.ts:663-702; owner decision
2026-10-09). Tests: "a host holding no result graph key names the key …"
and "with legacy workflow ids, …" (a missing task), and, added 2026-10-09
on claude/fix6-runbook-tests, "a COMPLETED A2A task without the message's
accepted artifact does not settle that message's binding: …" and "a settled
check that cannot read the A2A task store keeps the binding listed and
reported: …". Settled bindings are left
out of `underPreviousResultGraphKey`, and out of the `unknown-result-graph-key`
start lines and listing once their key is removed. A settled binding stays
recorded under its key; after that key is removed, re-publishing its
already published result is refused with the unknown-key error.

Settling is final, so a deployment checks a binding against its A2A task
store until it settles and never again (claude/fix6-hygiene). Each settled
binding is recorded per deployment in the additive table
`loop_supervisor_message_v2_settled_result_binding` (workflow id, A2A task
id, deployment), and the start report and the GET read only bindings not
recorded there. Before, every start and every GET re-checked every binding
under a non-primary key, and each rotation added more. A missing task, a
task without its accepted-result artifact and a failing read are never
recorded, so they are checked again each time. An older build never reads
the table; deleting its rows only makes the host check those bindings again
(supervisor-a2a-result-key-rotation, 20 tests on claude/fix6-hygiene and
22 on r6 integration with claude/fix6-runbook-tests' two: "a settled binding is
remembered durably: ..." and "a settled binding is remembered per
deployment: ...").

Authenticated `GET <routePath>/assignment` adds
`"underPreviousResultGraphKey": [{"a2aTaskId", "graphTaskId", "graphWorkflowId", "keyFingerprint", "messageWorkflowId"}]`:
this route tenant's unsettled bindings under a previous key of this
deployment. /healthz carries no binding, key or fingerprint.

Do not rename the task queue during a key rotation. The host's task queue
(`taskQueue`, the orchestration config key) is its deployment: the ledger
classifies, lists and reports only the bindings whose `bound_by_deployment`
is that name (or whose deployment-format message its start intent assigns
to it), and the settled record above is kept per deployment. A host
restarted under a new task queue name owns none of the bindings recorded
under the old name, so:

- `underPreviousResultGraphKey` and the `unknown-result-graph-key` start
  lines stop naming them, and the retirement check below passes while
  bindings under the previous key are still waiting to publish. Removing
  that key then strands them: they can never publish;
- deployment-format message ids are minted for the deployment, so messages
  started under the old name are another deployment's messages to the
  renamed host;
- every binding is checked against the A2A task store again, once, under
  the new name.

Keep the task queue name unchanged from step 1 of the rotation until the
retirement check has passed and the previous key's variable is removed. If
a rename is needed, do it on its own, outside any rotation, after every
previous key has been retired and every binding the host still lists has
settled.

Rotation procedure:

1. Before rotating, bind every result graph already started under the
   current key. A graph started but not bound when its key becomes a
   previous key can never be bound; it must be started again under the new
   key. Each start reports such a graph that `resultArtifacts` lists:
   `A2A V2 result graph cannot be bound (started-under-previous-result-graph-key): ...`.
2. Put the new key in the secret store under a new variable name. Set
   `resultGraphKeyEnv` to it and add the old variable's name to
   `previousResultGraphKeyEnvs`, on every host of the deployment. Keep every
   existing `resultArtifacts` `graphWorkflowId` as it is; compute ids with
   `loop orchestration result-graph-id` only for messages not bound yet.
3. Restart each host. Check with `result-graph-key-fingerprints` that the
   old fingerprint is `previous` and the new one `primary`.

Retirement check, before removing a previous key's variable, on each route
tenant of the deployment:

1. `loop orchestration result-graph-key-fingerprints <config-path>`: note
   the fingerprint of the variable to remove.
2. Authenticated `GET <routePath>/assignment`: no entry of
   `underPreviousResultGraphKey` has that `keyFingerprint`. Each remaining
   entry is a binding whose result has not been published yet; wait for it
   to publish, or for its A2A task to end, and check again.
3. The latest start log has no `started-under-previous-result-graph-key`
   line naming that fingerprint.

Then remove the variable from `previousResultGraphKeyEnvs` (and the secret
store), restart, and confirm the start log has no `unknown-result-graph-key`
line naming that fingerprint (test "a previous key is no longer needed once
every binding under it has settled: ...").

## Dead-run workspace release

A run hands its workspace back (`workspaceReleasedAt`) only when its tmux
session is positively gone and no recorded process of the run can still be
live. The same evidence is used by `loop reconcile stopped-run|failed-terminal
<runId>`, the launch auto-release of a dead stopped or failed run, the clean
teardown's own handback, and startup GC. Recorded processes are:

- the run pid and launch-attempt pid (manifest), and the Codex app-server;
- the bridge worker (`bridge-worker.json`) and each `run-processes/` entry
  (bridge MCP processes);
- each agent pane's process GROUP (`run-processes/pane-<pane>-<pid>.json`,
  written at launch, on a resume that re-attaches, and by the teardown before
  its session kill; never the governess pane);
- the process GROUP of every descendant of an agent pane process that is not
  in the pane's group (`run-processes/agent-group-<pgid>.json`). The real
  CLIs start their tool subprocesses outside the pane group: Claude Code runs
  each Bash tool shell as a session leader, and Codex runs each exec command
  and MCP server in a group of its own. These groups are found by a ppid walk
  over one `ps -axo pid,ppid,pgid,lstart` snapshot while the CLI is still the
  parent: at launch, on a re-attach, on every governess cycle (at most every
  5 s), and by the teardown right before its session kill. A pane process is
  walked only while it is provably the recorded one (same group, started by
  the record). A group is provably the recorded one while some member started
  by the record's instant lives; each snapshot moves the instant of every such
  record (pane or descendant) up to itself, carrying identity forward after
  the original members exit. Records of groups that are gone are pruned by
  later snapshots;
- each claimed utility job's worker process GROUP (`utility/jobs.jsonl`; a
  worker is spawned detached, so its group id is its pid).

A recorded group is live while any member exists, even after its leader is
gone. A live process that provably started after the recorded instant and
holds the group's id is not the group (a pid is never allocated while a group
with that id exists).

A teardown signals the utility workers' groups (identity: the worker command
with this exact run directory, epoch and job id) before the session kill.
Right before the kill (after the beat close, when Temporal is on) it records
the agent panes and their descendants' groups. After the kill it ends the
worker groups and every recorded agent group that is provably the recorded
one in that snapshot (one that is not is logged `agent-group-unverified`,
never signalled, and still blocks the release while it lives): SIGTERM, a 3 s
grace, SIGKILL, a 1 s wait. Right before each signal
round every agent group is re-identified on a fresh process table: it is still
the recorded group only while some member started by the snapshot instant
lives (a reused group id has only later members), and a target that no longer
is is reported `unverified` and never signalled. The handback then re-reads
every record. Stale recovery ends a timed-out or stale-epoch worker's group
the same way (re-identified before its SIGKILL). Startup GC writes a handback
only on the full evidence above; a never-bound launch it cannot release yet
stays active, so the next GC judges it again. `loop reconcile` re-verifies a
recorded handback on the full evidence before it answers `already-released`.

`bridge-worker.json` never stops naming a live process while a worker may be
starting: before the spawn it names the spawner (`"pending": true`), right
after it the new worker, and a worker that finds a record naming no live
process records itself.

### Dead-run release: accepted residual risks (2026-10-10)

The owner accepted these on 2026-10-10 when choosing to close the remaining
review gap with the process-group repair and then install:

- A socket-less legacy run is judged on every candidate socket plus all
  recorded evidence being dead.
- A torn last `utility/jobs.jsonl` line older than 60 s is ignored.
- A malformed complete `utility/jobs.jsonl` line blocks release until it is
  repaired.
- A recycled pid (or process group id) can falsely block a release; it never
  falsely grants one.
- Utility workers started by the old binary (ea968d82) lack the claim-time
  self-cancel on a terminal run.
- A resume or re-stop between a release's read and its write is not modelled.
- Startup GC pays for tmux probing of each candidate run.

Further limits of the same repair, recorded for the owner (not part of the
2026-10-10 acceptance; they need the owner's decision):

- Runs launched before pane records existed have none: until a resume
  re-attaches (or, for a run that recorded its socket, a governess started
  from this binary tears it down), they are judged as before, on session
  absence plus the other evidence. A governess already running from the old
  binary tears down with the old code and takes no descendant snapshots.
- A tool subprocess is tracked through its parent chain to the CLI. One that
  both leaves every recorded group (setsid) and loses that chain (its parent
  exits, as in a double fork) between two snapshots, at most about 5 s apart
  while the governess runs, is not seen. So is one started in the
  milliseconds between the teardown's last snapshot and the CLI's death on
  the hangup. If the governess is gone (crashed), no periodic snapshots are
  taken.
- Group identity before a signal is judged at `ps`'s one-second start-time
  resolution: a group id that is freed and reused within the same wall-clock
  second as the snapshot could be taken for the recorded group. A process
  older than the snapshot that voluntarily joins a newer group of its own
  session (setpgid) would make that group look recorded too.
- A worker group whose leader is gone before the teardown cannot be
  identified by its command, so it is never signalled automatically; it blocks
  the release until it exits or the operator ends it.
- Pane records are never removed: `run-processes/` gains one file per pane
  process (a respawn adds one). A malformed pane or descendant group record,
  or one naming a group id of 1 or less, is unreadable evidence: it blocks
  the release until the operator repairs or removes it.
- A pane that the manifest does not name (split in by hand) is not recorded.
- The other side of tracking descendants: a long-lived daemon a tool started
  from inside the run (a `gpg-agent` while it still descends from the CLI, a
  dev server) is run-owned once a snapshot saw it, unless one of the
  shared-process rules below applies. Its life blocks the release, and the
  teardown ends it.
- Not verified: whether the Claude or Codex CLI itself ends its detached tool
  children on a hangup. The repair does not rely on it.

### Shared processes: whose is it (2026-10-10)

How a Codex seat gets its app-server (from the code, `tmux.ts`
`preparePersistentTmuxLaunch` and `codex-app-server.ts`): each paired launch
or resume that includes Codex has its launcher process (the `loop` command)
spawn one `codex app-server --listen ws://127.0.0.1:<port>` detached (its own
session and group) and orphaned when the launcher exits. Its pid and URL are
recorded as the run's `codexAppServerPid` / `codexRemoteUrl`, and the
launcher also spawns a detached `loop __codex-tmux-proxy <runDir> ...` that
the Codex pane connects through. Nothing in the code shares one app-server
between runs or seats on purpose: the app-server object is a singleton per
launcher process, and each run has its own launcher. Sharing comes from the
process tree: a `loop` launch or resume of run B run from an agent's tool
shell in run A starts B's app-server, B's proxy and, for a private socket,
possibly B's tmux server as descendants of A's agent CLI, so A's ppid walk
recorded them as A's `agent-group-<pgid>.json`. Other long-lived processes
that can appear in an agent pane's tree: the agent CLIs' MCP servers
(`loop __bridge-mcp <runDir>` and configured ones, children of that CLI), the
bridge worker and utility workers (spawned detached from inside the tree,
their command line names their run directory), and whatever a tool starts
(dev servers, Temporal dev servers, build daemons such as Gradle, watchman,
`lms server start`, `docker` clients). The governess pane, which runs the
governess helpers, is never walked.

Another run is provably dead (and then ignored) only on the release's own
evidence, never on its manifest alone: its manifest is readable and terminal
(stopped, failed, completed), AND its pid, launch attempt and every process
and group it records (`codexAppServerPid`, `bridge-worker.json`,
`run-processes/` records, utility worker claims) are gone from one process
table snapshot or are provably later processes (started after the later of
its handback and its last update, or after the record's own instant; a group
with its leader gone is live while any member lives), AND its tmux runtime is
positively gone by the release rule (`tmuxRuntimeAbsentForManifestSync`; a
never-bound launch has none). A terminal run that fails any of these, or
whose records cannot be read, is live for these rules: what it records is
never ended by another run's teardown. Since 2026-10-10 (after 688da14f);
before that a terminal manifest alone made a run dead.

The rules (`src/loop/shared-process-ownership.ts`), first match wins:

0. The A2A V2 orchestration host (r6 line, added when the dead-run hotfix was
   ported onto claude/fix-integration-r6-2026-10-09): `shared-process-skipped`
   with `otherRunId` `orchestration-host` when a member, or any process up a
   member's whole parent chain (not stopped at the pane processes), runs
   `loop orchestration serve <config>` (the compiled binary under any name
   starting with `loop`, or `src/cli.ts`) or `src/orchestration-cli.ts`. The
   host is normally the launchd agent `com.harness.loop-orchestration` and is
   then never in a run's tree at all; the rule covers a host started from an
   agent's tool shell, one running in a pane's group, its headless wake
   sessions, and a run a wake launched (its app-server while the launcher
   still runs). It applies to every record kind (walked groups, pane groups,
   the manifest app-server, worker targets) at collection, at every signal
   round and in the release evidence: never signalled; release evidence only
   while a member's cwd is inside this run's workspace or cannot be read. It
   needs no other run, so it holds while other runs are unreadable. Limits: it
   is judged on the check's command lines (`ps -axww -o pid=,command=`);
   without them rules 1 to 4 decide alone, and a host renamed so that neither
   form matches is judged like any other process. The host's Codex delivery
   reaches each run's app-server over its recorded `codexRemoteUrl` and starts
   no app-server of its own, so a run's bound app-server stays that run's.
1. `shared-process-skipped`: another run that is not provably dead records
   the process or its group (manifest pid, launch attempt, `codexAppServerPid`,
   `bridge-worker.json`, `run-processes/` records, utility worker claims), or
   a member's command line names that run's directory, tmux socket, tmux
   session or `--run-id`. For a walked group (`agent-group-*`) the same test
   is applied to every ancestor of a member, up to launchd or to this run's
   own recorded pane processes (never above them, into the tmux server): a
   child that B's app-server or B's tmux proxy started in a group of its own
   is B's too, even though no run records the child. A record whose id is
   held only by processes started after it names a later process and does
   not apply. This run's own tmux session, socket and run id never count as
   naming another run (runs on one tmux server share its socket). For the
   run's own explicit records (its pane groups, its manifest
   `codexAppServerPid`, its bridge and utility worker targets) another run's
   ppid-walk records (`agent-group-*`) do not count: that run only saw the
   process descend from its panes because this run was launched from one of
   them, and this run's teardown must still end its own app-server. The
   teardown never signals a shared process: not at the pre-kill collection,
   not the run's own `codexAppServerPid` cleanup, and not in any signal
   round (each round re-reads the other runs and the process table). The
   governess logs one `shared-process-skipped` line per skip with
   `otherRunId` and the `phase` (`cleanup`, `collect`, `terminate`). It is
   release evidence only while a member's cwd (`lsof -a -p <pid> -d cwd`) is
   inside this run's workspace root (binding root, else cwd) or cannot be
   read.
2. `ownership-unknown`: the other runs cannot all be read (a run directory,
   a manifest or a run's records unreadable, in a run that is not provably
   dead), or the walked group is not in the process table. A walked group is
   then never signalled and stays release evidence. The run's own explicit
   records are judged by rule 1 on the runs that CAN be read (a readable
   live run that records or names one still makes it shared), and are
   signalled only when a positive identity binds them to this run, never
   because the other runs say nothing:
   - the manifest app-server (`codexAppServerPid`): the manifest records its
     exact listen URL (`codexRemoteUrl`); the live command line is
     `app-server --listen <that URL>` (whole arguments, or `--listen=<URL>`);
     the process holds that port's listener (`lsof -iTCP:<port>
     -sTCP:LISTEN`); and it started no later than the manifest's last update,
     on one process table snapshot. A manifest without `codexRemoteUrl`
     (runs recorded before it) is unproven. An unbound app-server is never
     signalled, whether or not the other runs can be read; the cleanup logs
     it as `app-server-identity-mismatch` with `detail: identity not proven:
     <why>` and, when other runs were unreadable, `; other runs unreadable:
     <reason>`. A bound app-server gets one SIGTERM, to its whole process
     group when the same snapshot shows it leading one that is not the
     cleanup's own (so the children Codex starts in it end too), else to its
     pid. One that is not running is skipped as `app-server-not-running`
     before the other runs are read;
   - a pane group: the run's own recorded pane, proven at collection (a
     member started by the record's instant) and re-identified against the
     snapshot instant before every signal round;
   - a utility worker target: its instant and its exact run directory,
     epoch and job command, re-checked before every signal round;
   - the bridge worker and bridge MCP processes: their command names this
     run's exact directory (checked right before their one SIGTERM).
   In the pre-signal check, an explicit target that carries no identity (no
   reference instant, no worker identity) is skipped as `ownership-unknown`
   while the other runs cannot be read.
3. `run-owned`: a pane group, the run's own manifest app-server (bound as
   above), or a walked group with a member still descending from one of the
   run's live, proven pane processes. As before: signalled after the kill,
   release evidence.
4. A walked group none of whose members descends from the run's panes is
   re-parented away only when every member's parent chain ends at launchd
   (pid 1), passing only through the group itself and the run's other walked
   groups. Any other parent (a process no run records) makes it
   `ownership-unknown`: never signalled, release evidence. A re-parented
   group is `reparented-in-workspace` (a member's cwd inside the workspace;
   signalled and counted as before), `ownership-unknown` (an unreadable cwd,
   or more than 32 members), or, with every member's cwd read and outside
   the workspace, `reparented-outside-workspace` (neither signalled nor
   counted) only if it was seen re-parented while its own pane's agent
   process lived: now, or by an earlier snapshot. Every walk snapshot (launch,
   re-attach, each governess cycle, the teardown's pre-kill collection)
   stamps `reparentedAt` on a walked record whose group it sees that way.
   A group first seen re-parented after its pane ended may be a tool orphaned
   by that end, or a group the teardown targeted and could not end (EPERM, a
   SIGKILL survivor): it is `ownership-unknown`, so it keeps blocking the
   release while it lives, as before this rule existed.

The release evidence applies rules 1, 2 and 4 only to the run's
`codexAppServerPid` and its `agent-group-*` records, in every release path
(`loop reconcile`, the launch auto-release, the teardown's own handback and
startup GC). The teardown's `workspace-released` detail lists each live
record it did not count and the rule.

Utility worker targets are re-verified right before every signal round, in
the teardown and in stale-worker recovery (`terminateUtilityWorker`) alike:
each carries the instant it was identified at (its group is still the
worker's only while a member started by then lives) and its identity (while
the leader lives, its command must still be the worker command of exactly
that run directory, epoch and job). One that fails is reported `unverified`
and never signalled; that includes the SIGKILL escalation after the grace.

Each signal round (`terminateTargets`) reads ONE process snapshot: one
`ps -axo pid,ppid,pgid,lstart` table and the command lines of that moment
(`ps -axww -o pid,command`, read only if a check needs them). The identity
re-check and the shared-process check of the round both judge that snapshot;
the SIGKILL round after the grace takes a new one.

Accepted and remaining risks of these rules (for the owner):

- A stale active manifest (a run that died without reconcile) keeps
  everything it records or names "shared" for every other run: never ended
  by them, and counted by them only while it works in their workspace. Its
  own reconcile ends this.
- The same now holds for a terminal run that is not provably dead (since
  2026-10-10): one whose teardown could not end a recorded process (EPERM,
  a SIGKILL survivor, an `unverified` or `agent-group-unverified` group), a
  run whose recorded pid or group id was reused by a process that started
  before its last update, or one whose tmux runtime cannot be proven gone
  (a reachable socket that does not answer about the session; a legacy
  socket-less run on any candidate server). Everything it records or names
  stays "shared" for every other run: never ended by them. It costs no
  release of its own (its release evidence is unchanged), but another run's
  walked group that it also records is left running until it is provably
  dead or the operator ends that process.
- One unreadable state anywhere under the storage root, in a run that is
  not provably dead (a torn `utility/jobs.jsonl` tail under 60 s old, a
  malformed `run-processes/` record, which is never pruned, a malformed
  manifest), makes every walked group of every tearing-down run
  `ownership-unknown`: never signalled, and blocking that run's release
  while it lives. The teardown runs once, and neither GC nor `loop
  reconcile` ever signals a walked group, so a moment of unreadability at
  the teardown leaves those tool processes running and the workspace held
  until they exit or the operator ends them. This fails closed by design.
  Since terminal runs are no longer dead on their manifest alone, a
  malformed record in an OLD terminal run whose processes are gone also
  counts (it is not provably dead), so the exposure is wider than before.
  The repair itself never reads live state. The second install review
  (2026-10-10, a read-only `readOtherRunIndex` call on the live root, by the
  reviewer, not by the repair) found 344 manifests there: 211 stopped, 117
  failed, 13 submitted, 3 input-required; 66 runs counted as live, about 50
  of them terminal but not provably dead. Every process those 50 record
  stays shared for every other run. Before relying on a release, the
  operator can check with a scan, for example `bun -e 'import {
  readOtherRunIndex } from "./src/loop/shared-process-ownership"; const r =
  readOtherRunIndex("/nonexistent", [process.env.HOME + "/.loop/runs"]);
  console.log(r.kind, r.kind === "unknown" ? r.reason : r.runs.length)'`
  from `loop-fork/`. It writes nothing, but it reads the process table and
  asks each terminal run's recorded tmux socket (`has-session`) whether its
  session is gone, which for a socket-less legacy run includes the default
  tmux server.
- Cost: every read of the other runs now also checks every terminal run
  under the storage roots: its record files, and, for each run whose
  recorded processes are all gone, one tmux probe (a `stat` and a bounded
  `tmux -S <socket> has-session`; every candidate socket for a legacy run).
  Measured by the second install review on the live root (2026-10-10, the
  344 manifests above): 3.4 to 4.7 s per read. A teardown reads it several
  times: once for the agent-group collection, once for its own app-server
  (only when that app-server is still running: a gone one is skipped before
  the read), once per signal round (SIGTERM, then SIGKILL when something
  survives), and in release judgements that meet a shared or walked
  process. Startup GC reads it once per abandoned run whose app-server is
  still running. On that root a teardown therefore spends tens of seconds,
  not seconds, in these reads; the cost grows with the number of runs kept
  under the root, and pruning old run directories is the operator's lever.
- Command-line matching is textual. A tool of this run that merely names
  another live run (`tail -f <other runDir>/governess.jsonl`, `loop status
  --run-id 7`) is treated as shared, and so is every walked group below it
  while that tool's shell is its ancestor: this run's teardown leaves them
  running, and they block this run's release while their cwd is in this
  workspace. The operator ends them. A `--run-id` value equal to this run's
  own id never matches (ids repeat across repositories); one equal to
  another live run's id in any repository does.
- The motivating case releases only when the shared process works outside
  this run's workspace. A `loop` launch of run B from a tool shell in run A
  starts B's app-server with no explicit cwd (`codex-app-server.ts`), so it
  inherits the launcher's cwd: usually A's workspace, or B's worktree under
  A's root (`.worktrees/`, `.claude/worktrees/`). Its cwd is then inside A's
  workspace root, so A's teardown leaves it running but A does not release
  until B ends (or until it exits). The smoke and the release tests use a
  cwd outside A's workspace; the held case is pinned by the test "a shared
  daemon whose cwd is inside A's workspace blocks A's release".
- A daemon working outside the workspace (cwd elsewhere) that still writes
  into it by absolute path is not counted once it was seen re-parented while
  its pane lived, and is not ended.
- A daemon that re-parented away after the last walk snapshot that saw its
  pane alive (at most about 5 s before the teardown's own collection, which
  takes one more) cannot be told from a tool orphaned by its pane's end: it
  blocks the release while it lives, whatever its cwd, until the operator
  ends it. With the governess gone (crashed), no periodic snapshots stamp
  `reparentedAt`, so every daemon first seen re-parented by GC or the launch
  auto-release blocks the same way (the pre-repair behaviour).
- A walked group whose parent is any process other than launchd, this
  run's pane tree or the run's own walked groups (an unrecorded process of
  another run, a stranger) is never signalled and blocks the release while
  it lives.
- An explicit record of the run's own (pane group, manifest app-server,
  worker target) is still signalled while some other runs cannot be read,
  but only when a positive identity binds it to this run (rule 2) and no
  readable live run records or names it; another run's walk record of it
  never stops that. An unreadable run could still hold a non-walk record
  of it (it would have to record this run's exact app-server pid, or pane
  group id, in its own manifest or records); nothing in the code writes
  one, and a recycled id is rejected by the start-time binding.
- An app-server recorded without `codexRemoteUrl` (runs from before the
  URL was recorded) is never ended by its run's teardown or by GC: its
  identity cannot be proven. It counts as release evidence while it lives,
  so the run is not released until it exits or the operator ends it. (The
  code before this repair required the URL's port too, so such an
  app-server was not ended before either.)
- The app-server's start-time binding compares against the manifest's LAST
  update, not the moment the pid was recorded, at `ps`'s one-second
  resolution. A different process would have to hold the same pid, run
  `app-server --listen` on the same recorded URL and hold that port's
  listener, and have started before the manifest's last update, to pass.
- The bridge worker and bridge MCP processes are signalled on their exact
  run-directory command line alone; the other runs are not consulted for
  them (a command naming this run's directory is this run's by rule 1).
- Walk records go both ways: while A (whose walk recorded B's app-server)
  is live, a walked group of B that A's walk recorded too is shared for B as
  well, so neither teardown ends it until the other run is provably dead.
  B's own app-server is not affected (explicit record).
- The real-Codex smoke (2026-10-10, codex-cli 0.162.1, scratch
  `CODEX_HOME`, no login) showed the app-server starting a configured MCP
  server in a group of its own, and ending it by itself when the app-server
  got its run's SIGTERM. The teardown relies on that for MCP servers the
  app-server starts (they are not recorded by any run); other Codex
  versions are not verified. In one of two smoke runs the cwd probe
  (`lsof`) answered unknown for the app-server; unknown counts as release
  evidence, so that fails closed.
- The same smoke showed network activity on app-server start, with no
  login: Codex syncs its plugins (`git fetch` of the openai/plugins
  repository into `CODEX_HOME`), as children in the app-server's own process
  group. Signalling the app-server's pid alone left them running,
  re-parented to launchd, for about 20 s. Since the third repair the run's
  own teardown and GC signal the bound app-server's whole group when the
  snapshot shows it leading one (it is spawned detached, so it does), and
  only its pid otherwise. The third repair's smoke (same Codex, scratch
  `CODEX_HOME`, another run unreadable) found four plugin-sync processes
  (`git`, `git remote-https`, `git-remote-https`, a shallow `git`) in the
  bound app-server's group at its run's cleanup; all of them, the app-server
  and its MCP server were gone within 5 s, before the smoke ended anything
  itself. A child that leaves that group (setsid, as the MCP
  servers do) is not reached; nor is the app-server's group held as release
  evidence once its leader is gone (the app-server is recorded as a pid).
- The identity binding needs the recorded pid to hold the listener itself.
  The Homebrew `codex` (0.162.1) is a native arm64 binary that does. A
  `codex` on PATH that is a wrapper or a node shim, which starts the real
  server as a child, would leave the recorded pid (the wrapper) without the
  listener: its app-server is then never ended by its run's teardown or by
  GC (`app-server-identity-mismatch`, "does not hold the listener"), and it
  counts as release evidence while the wrapper lives, so the run is not
  released until it exits or the operator ends it.
- cwd is read once per judgement; a process can `chdir` later. `lsof` is
  slow (tens of ms per pid): it runs only for shared or re-parented groups.
- Other runs are read from the storage root under `HOME` and, for a run
  directory in the storage layout, from its own root. Runs kept under another
  `HOME` are not seen.
- The Codex tmux proxy and a private tmux server started by another run's
  launcher are not recorded by that run; they (and their descendants) are
  recognised as shared only by their command lines naming its run directory
  or socket.

### Tests never reach live state (2026-10-10)

The suite must not read the operator's storage root or reach a live tmux
server. Before the third repair it did both: the default other-run index read
`$HOME/.loop/runs` (with 344 runs there, `run-process-cleanup` failed 2 of 19
and one index read took seconds), and a plain `tmux kill-session` /
`has-session` from two tests went to the default server, because Bun fixes
`os.homedir()` and the environment `Bun.spawn` passes to children at startup:
a test's or preload's later edit of `process.env` (such as
`TMUX_TMPDIR`) reaches neither. `test:file` and `test:ci` now run each file
under `scripts/test-hermetic.sh`, which starts it with a fresh scratch `HOME`
and `TMUX_TMPDIR` and with `TMUX`, `TMUX_PANE` and `LOOP_TMUX_SOCKET` unset,
and `tests/setup.ts` refuses any other launch (`hermeticEnvGap`). Run tests
only through those scripts; `LOOP_TEST_CERTIFICATION_MODE=single-file bun
test <file>` alone is refused. Limits: a test may still name an absolute
socket path of its own (they use scratch paths), and the legacy-socket
candidates include `/tmp/tmux-<uid>/default` by design, so a test that
judged a socket-less run on the default probes would ask the default server
`has-session`. A tmux spy (a logging `tmux` first on PATH) over the whole
suite at the third repair (2026-10-10, 140 files) saw 29 calls: none named a
default socket, the four plain ones (no `-S`) went to the launcher's scratch
`TMUX_TMPDIR`, and the rest named the tests' own scratch sockets. Before the
launcher, the same four plain calls carried no `TMUX_TMPDIR` and so went to
the default server.

Flaky, not regressions: two `launch-reservation` tests ("exact Run 61
releases on a live shared socket..." and "a present endpoint with unknown
liveness blocks...") failed once at 607a3890 and passed on every rerun; the
base ea968d82 passed them on three runs.

## Verifying a build (provenance, 2026-10-10)

The compiled `loop` binary is not byte-reproducible, so its sha256 names one
build, not a commit. Measured on 1fee206e (bun 1.4.2, macOS arm64): two
builds from the same checkout had different sha256 (d1c4380c..., 6b77492a...),
and a build from a `git archive` copy of the same commit at another path
(own `bun install --frozen-lockfile`) had a third (457edf4c...). The build
embeds the checkout's absolute paths, and bun's bundler sometimes inlines
`__require.resolve("watchpack")` as the resolved
`<checkout>/node_modules/watchpack/lib/index.js` and sometimes not. The
build itself is unchanged; provenance is checked by comparing path-normalised
strings instead:

1. Check out the claimed commit cleanly (`git worktree add --detach <dir>
   <sha>`, or `git archive <sha> loop-fork | tar -x -C <dir>`), run
   `bun install --frozen-lockfile` in `<dir>/loop-fork`, and build with
   `LOOP_BUILD_OUTFILE=<scratch>/loop bun run build` (no install).
2. For each binary `BIN`, with `ROOT` the absolute `loop-fork` path it was
   built from (for an installed binary, the build record's checkout path):

   ```sh
   strings -a -n 8 "$BIN" | LC_ALL=C sed \
     -e "s#$ROOT#<root>#g" -e "s#$(dirname "$BIN")#<outdir>#g" \
     -e 's#__require.resolve("<root>/node_modules/watchpack/lib/index.js")#__require.resolve("watchpack")#g' \
     | shasum -a 256
   ```

   (the first expression replaces the checkout path with the token
   `<root>`, the second the output directory, and the third undoes the
   watchpack variance).
3. The binary is the claimed commit's build when the two normalised digests
   are equal. Any other difference is real: list it with `diff` of the two
   normalised outputs before accepting anything.

Evidence for the method: the three 1fee206e builds above normalise to the
same digest (prefix a6039da1e21c6653), and a control build of 688da14f
from a clean copy differs from them in 204 normalised lines (the source
change). Limits: the comparison sees printable runs of 8 or more bytes, not
code bytes or Mach-O metadata; it does not prove the same bun version or
dependency tree (both shape the strings, so a different one usually shows
as a difference, but not always); the build record must name the checkout
path. Comparing against the installed binary reads `~/.local/bin/loop`,
which this repair never did.
