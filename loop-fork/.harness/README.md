# Repo Harness

This directory stores repo-local Harness state for `loop-fork`: active task
metadata, parked ideas, hooks, and task indexes. Use the root `./harness`
wrapper from the repository root; it delegates to the scripts in `v2/kit/`.

For the agent-facing workflow guide, see `../HARNESS.md`.

## Research Behind This Copy

This Harness copy is downstream of Harness v2 research in
`/Users/amgad/dev_projects/harness-engineering`. The design was not imported
from a generic agent framework; it was derived from retrospectives on
`eye-tracker` and `ai-agent-tts`, then dogfooded in Harness source tasks.

The research found these recurring failures:

- Memory reset after compactions forced repeated rediscovery. Harness stores
  checkpoints under `runs/<task-id>/memory/` so a resumed agent has durable
  context.
- Long sessions mixed many features without task identity. Harness creates
  `.harness/current-task`, `runs/<task-id>/`, and completed `specs/<task-id>.md`
  artifacts around each unit of work.
- Real failures involved runtime state, not only source code. Harness added
  preflight checks, stop gates, eval dimensions, and state-invariant hooks.
- Emergent feature work and planned infrastructure work both happen in the same
  repos. Harness supports per-task modes instead of forcing every task through a
  spec-first workflow.
- Parallel agents were coordinating through conversation only. Harness records
  coordination and file intent in append-only JSONL artifacts.
- Bugs and security findings were not becoming durable regressions. Harness
  captures task logs, verification evidence, and regression-harvest prompts.
- Loop dogfooding exposed a root `PLAN.md` footgun. Harness loop handoffs should
  use run-owned prompt files generated by `./harness loop-prompt`.

External harness projects were reviewed as pattern research, not adopted as a
baseline. The source handoff explicitly chose not to fork external projects such
as Hive, OpenHarness, or AutoHarness because their README-level claims were
unverified and the target was a small, repo-native bash/python harness shaped by
the local workflow above.

Source pointers in the Harness source repo:

- `/Users/amgad/dev_projects/harness-engineering/docs/PROJECT-PAIN-DATA.md`:

## Quick Start

Check the current task state before editing:

```bash
./harness status --json
./harness list --status active
```

If there is no active task, create one:

```bash
./harness task task-slug --description "short description"
```

For planned work, create the task and initialize a run-owned plan:

```bash
./harness task task-slug --mode planned --description "short description"
./harness plan --init
```

## Work Loop

During implementation, keep the run directory current:

```bash
./harness checkpoint "short topic"
./harness coordinate editing --file path/to/file
./harness coordination --tail 20
```

Important run files:

- `runs/<task-id>/plan.md`: canonical plan for planned tasks.
- `runs/<task-id>/task-log.md`: what changed, why, proof, and regression notes.
- `runs/<task-id>/memory/`: numbered checkpoints.
- `runs/<task-id>/eval.json`: verification status.

Do not rely on root `PLAN.md` for Harness tasks. Harness-owned plans live in
`runs/<task-id>/plan.md`.

## Loop Prompts

When handing work to `loop`, generate a file-backed prompt from the active run:

```bash
./harness loop-prompt slice-slug \
  --slice "Implement only this slice." \
  --test-command "bun test tests/loop/bridge.test.ts"
```

Run the printed `loop --prompt runs/<task-id>/loop-slices/<slug>.md ...`
command. Prefer that over long inline `loop --prompt "..."` text because inline
prompt text can make `loop` create a root `PLAN.md`.

## Verification

Record proof through Harness so the evidence is durable:

```bash
./harness verify unit -- bun test tests/loop/bridge.test.ts
./harness preflight --json
./harness stop-gate --json
```

This repo's default required eval dimension is `unit`; see
`.harness/config.json`.

## Completion

Before closing a task:

```bash
./harness checkpoint "ready to complete"
./harness done
```

`done` requires the stop gate to pass, writes a completion spec under `specs/`,
updates `.harness/tasks.json`, and clears `.harness/current-task`.

## Parked Work

Capture future work without disturbing the active task:

```bash
./harness park "idea text" --name idea-slug
./harness promote idea-slug --mode planned
```

Park the active task when you need to switch context:

```bash
./harness park active-task-id
./harness activate active-task-id
```

## Research Gate

Large planned work should include reuse research before implementation:

```bash
./harness task task-slug --mode planned --estimate-loc 500 --description "short description"
./harness research --init
./harness research --save --file /tmp/research.md
./harness research --gate
```

The default research threshold is configured in `.harness/config.json`.

## Files In This Directory

- `config.json`: Harness settings for this repo.
- `tasks.json`: compact task index used by `./harness list`.
- `current-task`: active task marker, created only while a task is active.
- `hooks/`: optional hook entry points used by agents and wrapper flows.

Generated task artifacts are intentionally outside this hidden directory:
`runs/` holds in-progress work and `specs/` holds completed task specs.
